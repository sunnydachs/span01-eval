# 正規表現で足りる？"判定専用"AIモデルを試してみた

読み上げ用に書き出した原稿に、うっかり英単語が1つ混ざっていたことはありませんか。

私はこれで、合成音声がそこで不自然に読み上げてしまう事故を何度かやりました。

「日本語に英語が混ざっていないか」を判定したいだけなのに、意外と厄介です。

手で全部を確認するのは現実的でなく、正規表現で弾くのが定番だと思います。

そんな折、respan というサービスが「判定のためのモデル」を出しているのを知りました。

これなら先ほどの悩みも楽になるのでは、と思って実際に試してみました。

この記事はその記録です。結論から言うと、答えは場面で分かれました。

使ったコードと実測データは、こちらに置いています。

```
https://github.com/sunnydachs/span01-eval
```

## 先に結論

**境界ケースでは、モデルが正規表現に大差で勝ちます。**

ブランド名やURL、人名、略語が混ざった文では、
正規表現はこれらを全部「欠陥」として拾ってしまいます。

逆に**実際の原稿では、正規表現で足りました。**

ただしこの物差しは公平ではないので、あとで説明します。

なので実務の形は「正規表現を第一段、モデルを第二段」でした。
どちらか一方に決める話ではありません。

## そもそも、これは何か

respan が提供している、少し変わったタイプのモデルです。

公式サイトはこちらです。

- respan: https://www.respan.ai/

対象にしたのは span-01-lite というモデルです。

同系列の有料版 span-01 は、私のキーでは権限がなく測れていません。
以下本文の実測は、すべて lite 版です。

これは文章を生成するチャットモデルではありません。

**「ある条件に当てはまるかを、確率で返す」**モデルです。

自然文で「何を判定したいか」を定義して投げると、0〜1の確率が返ってきます。

分類器を、学習させずにプロンプトだけで作れる、という位置づけです。

> 判定のルールを、コードの中ではなく、日本語で書ける。
> これがこのモデルの売りだと、私は理解しました。

## 使えそうだと思った悩み

冒頭の悩みは、まさにこの形に当てはまりそうです。

やりたいのは「日本語の原稿に英語が混ざっていないか」の判定です。

従来のやり方は正規表現でした。実際、よく動きます。

ただし、静かに壊れる場所があります。

- 英単語が1つだけ、日本語に直接くっついている場合（取りこぼす）
- 逆に、ブランド名や人名、コード片を誤って検知する

この「取りこぼし」と「誤検知」を、
自然文で定義できるモデルなら減らせるのでは、と考えました。

## 実際に試してみた

思いつきではなく、比較できる形で測りました。

準備したデータは、2種類です。

1つ目は、境界線ぎりぎりの文を自分で作った合成スイート（23件）です。

英語の単語、英語の文、カタカナ語、ブランド名、人名、
URL、略語、コード片、ロール名を、1件ずつ並べました。

2つ目は、実際の日本語原稿です。約200件あります。

そのうち英字を含むものを全部と、含まないものを一部抜き出しました。

比べたのは、この3つです。

```
  [ 日本語の原稿 ]
        │
        ├─ 正規表現 ────── 決定的・0円・0秒
        ├─ 判定モデル ──── 自然文で定義 → 確率
        └─ 汎用チャット ── YES/NO で答えさせる
```

呼び出しは合計167回。課金は0円で、レート制限にも当たりませんでした。

## 結果: 境界ケースでは、モデルの勝ち

まず合成スイート23件です。

F1 は「取りこぼし」と「誤検知」を1つにまとめた指標で、1.0が満点です。

- 正規表現（この用途向けのパターン） ── F1 0.52

- 正規表現（英字2文字以上を全部拾う） ── F1 0.62

- 判定モデル（指示文が曖昧） ────── F1 0.67

- 判定モデル（除外を明示） ─────── F1 0.82

- **判定モデル（指示文を書き切る） ──── F1 0.93**

- 汎用チャットモデル ──────────── F1 1.00

**正規表現は大きく負けています。**

理由ははっきりしていて、正規表現は誤検知を9件出しました。

iPhone、YouTube、Instagram、URL、人名、`OK`、`AI`、`DX`。

どれも日本語の原稿として普通に出てくるもので、欠陥ではありません。

一方で、取りこぼしも2件ありました。日本語に直接くっついていない英語の文です。

「境界を判定する」という仕事は、正規表現には向いていませんでした。

## 結果: 実際の原稿では、正規表現で足りた

では実データ約200件ではどうだったか。ここは結果が反転しました。

- 正規表現 ──── 22件中 22件を検知

- 判定モデル ── 22件中 21件を検知

**ただし、この物差しは公平ではありません。**

ここでいう「正解」は「ラテン文字が含まれているか」そのものです。

含まない文を集めて「含まない側」と定義しているので、
ラテン文字を探すプログラムなら、何でも満点になります。

正規表現が強いのではなく、**正規表現の定義で採点していた**わけです。

実際の混入は「日本語に直接くっついた英単語」ばかりで、
その型に限れば4行の正規表現で全部拾えます。これは事実です。

ただ「正規表現のほうが優れている証拠」にはなりませんでした。

## いちばん驚いたこと

面白かったのは、精度ではなく**指示文の影響力**でした。

同じ「日本語に英単語が1つ混ざった文」でも、
指示文の書き方だけで、結果が反転します。

```
 「英単語が混ざっている」とだけ指示
   このmethodはやばい   →  確率 0.06   見逃し

 「単一の英単語も数える」と明示
   このmethodはやばい   →  確率 0.81   検知
```

さらに、指示に従わない場面もありました。

「すべての英字を検知せよ」と書いても、
ブランド名やURLは、なぜか除外され続けます。

モデルの中にある「これは除外してよさそう」という前提は、
指示文では完全には上書きできない、ということです。

> 自然文で定義できる、というのは諸刃の剣でした。
> 書けば書くほど良くなる。書かないと、静かに見逃す。

## 閾値の話を、ひとつ訂正

確率が返るので、どこで線を引くかが問題になります。

最初は「0.15と0.85の2本で判断する」と書くつもりでした。

実際に測ってみたら、それは間違いでした。

```
 閾値     F1      誤検知
 0.15    0.86     7件   ← 最悪
 0.50    0.89     4件
 0.70    0.92     2件
 0.85    0.83     2件   ← 取りこぼしが増える
```

0.15まで下げると、モデルが「もう出さない」と覚えたはずの
`OK` やコード片を、また拾い始めます。

閾値は0.5のままで十分でした。下げる理由はありません。

なお、この表の正解ラベルには実コーパス側の除外トークン
（作品内のキャラクター名）が含まれ、原稿が非公開のため同梱できません。

第三者が再現できるのは合成23件分だけです。
リポジトリの README に同じ注記を足してあります。

## 正直な限界

- 合成スイートは23件のみで、各1回だけの測定です。

- 2026-10-03 に全パイプラインを再実行し、本稿の全数値が同一であることを確認しました。

- 実コーパスは原稿の追加で件数が増えるため、実データの件数だけは測定時点で変わります。

- 0.93と1.00の差は**1ケース**です。順位づけの根拠にはなりません。

- 指示文は、この同じ23件を見ながら選んでいます（別のテストデータなし）。

- 正解ラベルは私ひとりの判断で、途中で1件直しました。

- 数字は公開前に、別のAIモデル5つに再計算させて誤りを修正しています。

## まとめ: どう使うか

結論はこうなりました。

**正規表現を第一段に置き、モデルは第二段で「境界の誤検知」を減らす。**

判定の流れにすると、こうなります。

```
  [原稿]
     │
     ▼
 {正規表現で検知?} ──はい──▶ [要修正]
     │いいえ
     ▼
 [判定モデルに投げる]
     │
     ▼
 {確率が0.5以上?} ──はい──▶ [要修正]
     │いいえ
     ▼
 [そのまま通す]
```

この形の利点は、次の3つです。

- 決定性と0円を、正規表現の段で確保できる

- モデルには「ブランド名を誤検知しない」役割だけを任せられる

- モデルを差し替えても、判定全体は壊れない

逆に、実データだけを見て「正規表現で足りる」と結論するのは危険でした。

私の原稿は今たまたま「隣接型」の混入ばかりだっただけで、
新しい書き方を覚えれば、正規表現の段は黙って落ちます。

なお、専用モデルである必要はありませんでした。

汎用チャットモデルでも、同じことはできます（要リトライ）。

ただし「除外ルールを日本語で書ける」という性質は、
正規表現では表現しづらい条件を扱うときに効いてきそうです。
